# Ablations

## Self-consistency term (offline, `scripts/ablation_consistency.py`)

**Question:** does the deterministic `consistency_i` term
(`or_select/consistency.py`) ever actually change which candidate wins,
or is it dead weight in the objective?

**Method:** fully offline, zero new API calls. Each saved
`selection.json` stores the final combined score but not the intermediate
`quality_i`; since the scoring formula is known exactly
(`score_i = w_quality*quality_i + w_confidence*confidence_i +
w_consistency*consistency_i - w_cost*cost_i`), `quality_i` is recoverable
by inversion, subject to saved precision. This is not an independent recovery
or validation of the original pairwise matrix. Re-solving `select_best` with `consistency=None`
(dropping the term entirely) on the same recovered `quality_i` and saved
`confidence_i`/`cost_i` isolates the term's effect in this reconstructed model.
The script asserts the reconstructed full-model
winner matches the originally saved winner as a correctness check before
reporting the ablated result.

**Result: 0/3 winners changed** (corrected — see data-hygiene note below).

| Query | Original winner | Ablated winner | Changed? | `consistency` spread |
|---|---|---|---|---|
| Rent vs. buy | c3 | c3 | no | 0.000 |
| Hamlet summary | c2 | c2 | no | 0.000 |
| Traffic congestion | c1 | c1 | no | 0.000 |

**Data-hygiene correction:** the first pass of this ablation globbed
*every* file under `outputs/runs/*/selection.json` and reported "0/5."
Two of those five (`capital-of-france`, `berlin-wall-year`) were written
at 14:56 and 15:28, before the exact-match short-circuit and
self-consistency-term wiring were committed at 16:19 — i.e. they were
generated by an *earlier version of the pipeline* that didn't have a
`consistency_i` term at all, and their pairwise scores were the direct
product of live-judge variation (identical text scored
0.375/0.50/0.625 rather than the 0.5 assigned by the later exact-match bypass).
This observation does not isolate a provider's seed handling.
Reconstructing `quality_i` from those files' saved scores using the
*current* formula silently mixed pre-fix and post-fix semantics, and a
live re-run of the permutation ablation on the same stale
`capital-of-france` file produced a "changed" result driven entirely by
CP-SAT's arbitrary tie-break among five now-identical (correctly
short-circuited) candidates, not by any real judge signal — an artifact,
not a finding. Both stale files are excluded from both ablations; only
the 3 genuinely post-fix Track A runs are used. The corrected result
(0/3) matches the original headline number by coincidence, not because
the mistake was harmless — it needed to be caught and fixed regardless.

**Why, structurally, not just by chance:** `consistency_spread` — the gap
between the highest and lowest `consistency_i` in a run — was exactly
**0.000 in all 3 valid cases**. The term can only change a ranking if it
assigns *different* values to different candidates; a constant added to
every candidate's score never changes which one is the argmax. Spread was
zero because every candidate set in these 3 runs was fully diverged
(unique text, flat `1/N` for everyone). The term is designed to matter
in the middle case — some candidates cluster into groups of *uneven*
size — which did not occur in these three valid pilot runs.
`tests/test_selection.py`'s
`test_consistency_can_flip_a_close_tie_toward_the_majority_answer` proves
the term *can* change a winner given synthetic data shaped that way; this
ablation does not establish its effect on later benchmark runs.

**Pilot interpretation:** with `w_consistency=0.3`, the term is constant
within these three pools. The ground-truth tracks later produced uneven majorities; the term is
included in the offline weight replay below (the `SC+quality` and `No cost`
variants), where it is not inert.

## Permutation self-consistency (position-bias correction)

**Question:** does bidirectional judging (forward + backward, averaged)
actually change the winner versus naive single-direction judging?

**Method:** live, `scripts/ablation_permutation.py`. Forward-only judge
calls against the same already-saved candidate texts used above; compared
against the existing bidirectional result already saved in each
`selection.json`. Same data-hygiene scope as above: only the 3 post-fix
Track A files are valid inputs.

**Final result: 2/3 winners changed.**

| Query | Bidirectional winner | Forward-only winner | Changed? |
|---|---|---|---|
| Rent vs. buy | c3 | c4 | **yes** |
| Hamlet summary | c2 | c0 | **yes** |
| Traffic congestion | c1 | c1 | no |

The recorded live comparison changes the selected candidate in two of these
three pilot cases. It does not isolate a causal position-bias effect: the
forward-only calls were fresh rather than matched stored directional calls.
There is no ground-truth accuracy label, and three examples cannot establish
how often bidirectional judging helps.

## Weight ablations on the ground-truth tracks (offline, `scripts/ablation_weights_offline.py`)

**Question:** which term of the objective drives the winner, and does removing the cost term help?

**Method:** the stored-judgment subset carries candidate texts, confidences and the pairwise matrix, so
`or_select.selection.select_best` is replayed under other weights with zero API calls. Fidelity compares
extracted final answers, not exact candidate identities. Current coverage and fidelity are generated in
`manuscript/Ablation_data.tex`. Variants: the default weights; no cost term; weighted-win quality alone; plurality
vote with Copeland quality as the tie-break.

**Result and interpretation:** see the manuscript's objective diagnostics and `manuscript/Ablation_data.tex`. The cost term
(word count) usually has a larger within-pool spread than quality. That alone does not prove which term determines the winner. Removing cost does not make judge-based selection beat
plurality voting in heterogeneous pools. These ablations are post hoc and exploratory.
